# /compact 上下文压缩 —— 开发大纲

> 对应包号 0.0.4 · 需求与阈值已定 · 本文是这一版的开发依据
> 剩余待确认项在 §6（只剩 `glm-5.3-flash` 的窗口值，不挡开工）
> 功能背景与验收见 `docs/PRD.md`；分层约束见 `docs/DESIGN.md` §1–§2

## 0. 已定的数值

| 项 | 值 |
|---|---|
| 自动压缩阈值 | `min(窗口 × 80%, 200000)` |
| 压缩后保留 | `min(窗口 × 16%, 40000)`，且不低于 20000 |
| 取不到窗口值时的保留量 | 固定 20000 |
| 超限错误关键词 | `context length` / `maximum context` / `too many tokens` / `prompt is too long`，忽略大小写，配合状态码 400 |
| 超限后重试次数 | 整轮 1 次 |
| 序列化时单条工具结果截断 | 2000 字符 |
| token 估算 | CJK 字符按 1 token，其余按 4 字符 1 token |

比例取自 pi 与 dsh，绝对上限取自 Codex 的 `min(配置值, 窗口 × 90%)` 思路。加上限是因为三家现在都是 1M 窗口，纯比例会变成「烧到 80 万 token 才压缩、压完还留 16 万」，不实用。加上限后 128K 窗口的行为与纯比例一致（102,400 触发、20,480 保留），只有 1M 这一档被收到 20 万触发、4 万保留。

## 1. 整体思路

一句话需求：长会话不要因为上下文涨满而失败。

拆成四块，按数据流串起来：

```
每轮用户输入
   │
   ├─①估算：上一条 assistant 的 usage 超过阈值？ ──是──┐
   │                                                     │
   ├──否──────────────────────────┐                     │
   │                               │                     ▼
/compact 命令 ───────────────────► ②压缩 ◄───────────③超限兜底
   │                               │  切点 → 摘要 → 换内存 + 写文件
   │                               ▼
   └────────────────────────► 发请求（agentTurn）
                                   │
                                   └─失败且是「上下文超限」→ ③压一次，重发本轮（只一次）
```

- **①估算**是纯计算，不改任何状态，只回答「该不该压」。
- **②压缩**是唯一改状态的地方：内存 `messages` 换掉，会话文件追加分隔与摘要。
- **③兜底**在请求失败之后，复用②。
- **④窗口配置**是①的输入，取不到就整块自动压缩关闭。

三个入口最终都汇到②这一个函数，避免三套逻辑各写一遍。

## 2. 需求覆盖

| 需求 | 由哪块实现 | 判定标准 |
|---|---|---|
| 手动压缩 | `/compact`（§3.3） | 敲命令后屏幕出现 `compacted · A → B tokens`，B 明显小于 A |
| 自动压缩 | §3.2 + §3.3 | 估算超过阈值时，这一轮请求前先打出压缩行 |
| 用当前模型 | §3.3 | 压缩请求的 model 与底栏一致；`/cost` 累计值包含这次 |
| 屏幕只显示压缩记录和前后 token | §3.3 | 只有一行 `compacted · …`，没有消息条数，历史不清屏 |
| 原文保留、跨进程生效 | §3.3 写盘 | `cat` 能看到压缩前原文；`--resume` 后载入的条数等于压缩后内存里的条数（摘要 + 保留段） |
| 重复压缩合并 | §3.3 | 连压两次，第二次摘要含第一次的内容，不是两段并列 |
| 超限报错兜底 | §3.4 | 造一次超限错误，屏幕先出 `context overflow · compacting and retrying`，随后这一轮正常完成 |

## 3. 实现逻辑

### 3.1 模型窗口（新增配置）

这一块是后面三块的前提，没有它自动压缩无从判断。

`CatalogEntry.models` 里每一项现在只有 `{ id }`，要加窗口大小字段（新增）。`settings.json` 的 `providers.<name>.models` 写法相同，沿用现有「settings 盖目录」的优先级，不需要改 `resolveProvider` 的合并逻辑，只需让它把选中模型的窗口值一并带进 `ProviderConf`（新增字段）。

查到的官方数值（2026-09）：

| 模型 | 窗口 | 来源 |
|---|---|---|
| `deepseek-v4-flash` | 1,000,000 | 官方模型表 1M，输入输出共享 |
| `deepseek-v4-pro` | 1,000,000 | 同上 |
| `kimi-k3` | 1,000,000 | 平台文档，K2.6/K2.7 的 256K 之外的新旗舰 |
| `glm-5.3` | 1,000,000 | 智谱文档 1M，最大输出 128K |
| `glm-5.3-flash` | 待确认 | 官方未单独列出；同代 GLM-5.1 是 200K |

取不到窗口值时（用户自己加的模型、或目录项没写），①直接返回「不需要压缩」，自动压缩对这个模型静默关闭，手动 `/compact` 仍可用——这时保留量用固定的 20000 兜底。

### 3.2 估算与切点

这一块只做判断和计算，不发请求、不改数据，可以独立测试。落点是新文件 `src/core/compact.ts`（新增）。

**该不该压**：从 `messages` 末尾往前找最后一条 **usage 非零**的 `assistant`（被中断的那条是 0/0，要跳过），取它的 `usage.input + usage.output`，再加上它之后所有消息的估算值（可能有工具结果、`[interrupted]`）。这是上一轮真实发出去的量，比自己数字符准得多。这个值超过 `min(窗口 × 80%, 200000)` 就该压。历史里还没有 assistant（首轮）就不压。

**usage 有过期的时候。** 保留段里的 assistant 还带着压缩前的上下文大小；`--resume` 载入的 assistant 带的是上个进程的数字。不处理的话，压缩或恢复之后第一句话一进来就会再判超线，把刚生成的摘要再摘要一遍。所以压缩完、恢复完都要把当时数组里的 usage 标成不可信（`distrustUsage`），只信之后新产生的 assistant；`/clear` 时清掉标记。没有可信 usage 就不自动压，等下一条回复带来新数字。

这里有一个前提要先修：**`anthropic.ts` 现在只取 `input_tokens`**，不含 `cache_read_input_tokens` 和 `cache_creation_input_tokens`。Kimi 有自动缓存，命中时 `input_tokens` 只剩未命中的那一小截，估算会严重偏低，自动压缩永远不触发。要把三项加总写进 `usage.input`。OpenAI 兼容端的 `prompt_tokens` 本身已包含缓存部分，不用改。

**切在哪里**：从最新一条往前累加每条消息的估算大小，累计到保留量 `min(窗口 × 16%, 40000)`（不低于 20000）就停在这里。这一点及其之后的消息保留，之前的全部交给模型做摘要。

估算规则：CJK 字符每字 1 token，其余每 4 字符 1 token。pi 那套纯 `chars/4` 对中文会低估三倍左右，保留段实际会比预期大很多。

切点有一条硬约束：**只能落在 `user` 或 `assistant` 上，绝不能落在 `toolResult` 上**。工具结果必须紧跟发起它的那次调用，单独留一条孤立结果，下一轮请求会被接口拒掉（现有 `sealTools`、`repairMessages` 防的就是这件事）。所以往前累加时如果停在了 `toolResult`，继续往前退到最近一个合法位置。退完再检查保留段头部：若它是个对应调用已被切走的 `toolResult`，直接丢掉这一条。

摘要段内部不必补配对——整段会被一条摘要替换，里面的调用和结果都不会再发给模型。

**压不动的情况**：切点算下来等于 0（所有内容都得留），或摘要段为空，说明没有可压的东西。不发请求，提示一句后原样返回。典型场景是历史里只剩一条摘要加一条巨大的工具结果——根子在单条工具输出太大，属于工具截断的范畴，这一版不处理。

### 3.3 压缩本身

唯一会改状态的地方。入口三个：`repl.ts` 的 `/compact` 命令、每轮输入前的自动检查、请求失败后的兜底。三者调同一个函数。

**自动检查的时机要在 `pushMessage(user)` 之前。** 若先 push 再压，用户这句会落在分隔之前，`--resume` 读不到它。顺序是：检查 → 该压就压 → 再把用户这句 push 进去。

**请求怎么发**：复用现有 `callLLM`，`onText` 传空操作——不新增非流式分支，也不让压缩过程在屏幕上刷字。用当前 `getProvider()`，不另配小模型。要压的那段对话先序列化成一段文本，包在标签里，后面跟压缩指令，整体作为**一条 user 消息**发出去。关键点是不能把历史当成对话原样发，否则模型会顺着往下聊而不是做摘要。

这次请求有三处和正常对话不同：

- **system prompt 用一段独立的短文本**（"你是压缩引擎，只输出摘要，不调工具"），不用编码助手那段，否则模型会想动手。
- **不带工具。** `callLLM` 的 `tools` 传空。但现在 `openai.ts` 会把空数组原样发成 `tools: []`，部分兼容端点会 400——两个协议文件都要改成数组为空时省略该字段。
- **序列化时每条工具结果截到 2000 字符。** 摘要不需要完整输出，这一刀能把压缩请求本身的 token 省掉一大半，1M 窗口下兜底触发时也不至于压缩请求自己再超限。

**回应怎么算成功**：`stopReason` 必须是 `stop`，且有非空文本。`length`（摘要被截断，尾部的"下一步"段会丢）、`incomplete`、`badArgs`、或者模型给了 toolCall，都按失败处理。

**usage 怎么进 `/cost`**：现在 `tokenTotals` 从 `messages` 里的 assistant 求和。压缩之后被摘要掉的 assistant 消失，压缩请求自己的回应又不进 `messages`——`/cost` 和底栏的 session 数会变小。`repl.ts` 加一个进程内的结转计数，压缩时把「被压掉的 assistant 的 usage 总和 + 压缩请求的 usage」加进去，`tokenTotals` 输出时并上。`/clear` 和 `/resume` 时清零。跨进程不保留，这是已知取舍。

**要模型写什么**：固定分段，缺的段写 `(none)` 而不是省掉——分段固定，下次合并时才好对齐。八段：原始意图、关键技术点、涉及文件与改动、出过的错与怎么解决、待办、当前进度、下一步、关键约束与决定。明确要求原样保留文件路径、命令、报错原文、函数名。不数字数，靠生成上限约束长度。

**拿到摘要之后，按顺序做四步**：

1. 写分隔行（`session.ts` 已有的 `markCompact`，目前没有调用方，这一版补上它的第一个调用方）
2. 摘要作为一条 `user` 消息追加进文件
3. **把保留段重新追加一遍**
4. 内存 `messages` 换成「摘要那条 + 保留段」

第 3 步是关键。`loadMessages` 只读最后一道分隔之后的内容，而保留段原本在分隔之前——不重新追加，`--resume` 回来就只剩一条摘要，保留的那几万 token 全丢了，内存和文件对不上。代价是文件每次压缩多长约 160KB（4 万 token 的保留段），几次压缩离 32MB 上限还很远。

第 1、2 步的顺序也不能反：分隔必须先落盘，否则摘要会和它前面的原文一起被读进来。

摘要正文用固定标记包起来，供下一次压缩识别。摘要前面带一句框定："以下是此前对话的压缩记录，视为已知背景，直接继续，不要复述"——不然模型会把摘要当成用户的提问去回应。

**`writer` 为空时**（之前落盘失败过）：只改内存，不写文件，沿用 `takePersistError` 那条提示。不要为摘要去 `createSession`——文件名会变成摘要的第一行。

**重复压缩**：第二次压缩时，历史里那段旧摘要会落在摘要段里一起发给模型，指令额外要求把它合并进新摘要、丢掉已经过时的条目，而不是产出两段并列的摘要。

**屏幕上**：只打一行 `compacted · 48,200 → 9,600 tokens`。自动触发时前面加触发标记。不打消息条数，也不清屏。

**TUI 里 `/compact` 要设 busy。** 现在斜杠命令一律不 busy，而 Esc 只在 busy 时才 `abort()`——不设的话压缩过程打不断，底栏也不显示 `esc interrupt`。`repl.ts` 里把 `/compact` 和聊天同样对待。

**失败与中断要分开处理**：压缩请求共用本轮的 `AbortSignal`。三种结果：

| 结果 | 内存/文件 | 之后 |
|---|---|---|
| 被 Esc / Ctrl+C 打断 | 不动 | **整轮停下**，不发请求。中断是用户的意思，不能当失败绕过去 |
| 请求失败、模型没给出可用文字 | 不动 | 手动：报错。自动：报一句后照原样把请求发出去，宁可贵一点也不把话堵死 |
| 成功 | 按上面四步改 | 继续 |

宁可这次不压，也不能写进一段空摘要把历史弄丢。

### 3.4 超限兜底重试

§3.2 按比例估算，但工具结果特别大、或窗口值配错时照样会撞上限。现在这类错误从 `agentTurn` 直接抛到 `repl.ts` 红字报错，历史没变，再问一次还是撞——这一块补这个洞。

**怎么认出来**：请求失败时检查错误消息。两个协议文件在响应不 ok 时抛的都是 `API error ${status}: ${body}`，状态码和响应体都在消息里，够用。判据是状态码 400 配合响应体里出现下列之一（忽略大小写）：`context length`（DeepSeek 写法是 `maximum context length is …`）、`maximum context`、`too many tokens`、`prompt is too long`（Anthropic 格式）。各家措辞不同，这几条覆盖两个协议的常见写法，做成一个数组方便以后加；认不出就当普通错误照原样报，不做额外动作。

**认出来之后**：屏幕提示 `context overflow · compacting and retrying`，走 §3.3 压一次，然后**在当前 `messages` 上重新进入 `agentTurn`**。**整轮只重试一次**——压完再撞就老实报错。那说明单条内容本身就超了，再压也没用。

超限可能发生在一轮中间：`agentTurn` 跑了几次工具后某一次请求才撞上。这时 `messages` 里已经有这一轮的 assistant 和工具结果。重新进入 `agentTurn` 后它会从当前状态接着循环（末尾是工具结果就再问模型），不是把用户那句重发一遍。切点算法保证保留段头部协议合法，所以接着跑是安全的。

**这一轮的 user 消息要保留**。现在 `repl.ts` 里的撤回条件是 `messages.length === afterUser`——压缩之后数组长度变了，这个下标已经失效。改成看**末尾那条是不是这一轮的 user 消息**（role 为 user 且内容等于这次输入）。判断顺序是：先试压缩重试，只有压缩或重试也失败了，末尾仍是这一轮的 user，才撤回。

`agent.ts` 不改。压缩发生在 `agentTurn` 之外（之前或失败之后），循环本身不需要知道压缩这件事。

## 4.1 已知风险

- **分隔写完、摘要没写完就崩**：`--resume` 会读到空历史（原文还在文件里但在分隔之前，不加载）。概率很低，接受。
- **文件随压缩次数增长**：每次多写一份保留段。32MB 上限下几十次都够，超了走 session 那边的「拒绝追加」。
- **`/cost` 结转跨进程不保留**：`--resume` 后只算载入部分。

## 5. 不做

自动压缩的开关和阈值配置项（这一版写死）、`/compact` 带自定义指令、pi 那种把一轮内部再切分的处理、dsh 那种单独裁剪工具结果的机制、摘要落进独立文件。
